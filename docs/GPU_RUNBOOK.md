# Ранбук для машины с видеокартой

**Целевое железо:** RTX 5070 Ti, 16 GB VRAM, 32 GB RAM.

Здесь запускаются **F3 и F4** из `PHASE2.md`. F1, F2 и F5 карты не требуют и могут идти
на ноутбуке — но если удобнее делать всё в одном месте, они и здесь пойдут быстрее.

Сначала прочитай `docs/CONTEXT.md` — там за пять минут что это за проект и что уже есть.

---

## Что помещается в 16 GB VRAM

Мы считаем в **float32** — это не педантизм, а условие валидности: измерено, что bf16
сдвигает матрицу расстояний на 0.02–0.05, ровно на порядок заявляемых эффектов.
Отсюда арифметика:

| Модель | fp32 | bf16 | Вердикт при fp32 |
|---|---|---|---|
| SmolVLM-2.2B | 9.0 GB | 4.5 GB | помещается свободно |
| Qwen2-VL-2B | ~8.8 GB | 4.4 GB | помещается |
| LLaVA-1.5-7B | ~28 GB | 14 GB | **не помещается** в fp32 |

Отсюда первый шаг ранбука: проверить, сохраняется ли проблема точности на CUDA.
Если нет — открываются 7B-модели и F4 становится сильно интереснее.

## Шаг 1 — проверка точности на CUDA (~20 мин)

**Это первое, что надо сделать, и от результата зависит план F4.**

```bash
uv run python scripts/vlm_precision_check.py --model HuggingFaceTB/SmolVLM-Instruct --device cuda
```

Скрипт сначала прогоняет контроль (fp32 дважды — детерминизм), потом сравнивает fp16 и
bf16 с fp32 по согласию матриц расстояний.

**Как читать результат:**

- Согласие bf16 **≥ 0.999** → на CUDA проблема не воспроизводится. Скорее всего потому,
  что тензорные ядра накапливают bf16-произведения в fp32, а MPS накапливал в bf16.
  Тогда **7B-модели становятся доступны**, и в F4 можно брать LLaVA-1.5-7B.
- Согласие **< 0.999** → остаёмся в fp32, модели до ~3B. F4 берёт Qwen2-VL-2B и
  что-то ещё двухмиллиардное вместо 7B.

Что бы ни вышло — **запиши результат в `docs/LAB_JOURNAL.md`**. Это готовый абзац
в Methods, и его почти никто не пишет.

## Шаг 2 — F3: SmolVLM-2.2B (~15–30 мин)

Арбитр расхождения по `ventral`: в 256M наклон был положительным у 7 из 8 испытуемых, в
500M — у 3 из 8. Третья точка масштаба превращает «разошлось» в тренд или в шум.

Переключить устройство в конфиге:

```bash
sed -i 's/^device: mps/device: cuda/' configs/vlm.yaml && grep -n "^device" configs/vlm.yaml
```

Запуск (256M и 500M уже посчитаны на ноутбуке — если ты скопировал `cache/vlm_activations/`,
они пропустятся автоматически; если нет, посчитаются заново, это быстро):

```bash
uv run python scripts/vlm_extract_activations.py --config configs/vlm.yaml
```

Затем анализ:

```bash
uv run python scripts/vlm_rsa.py --config configs/vlm.yaml
```

**Что смотреть:** таблицу наклонов по слоям LLM. Ключевая строка — `ventral` у
`smolvlm_2b`: положительный наклон и сколько испытуемых из восьми.

Ожидаемое время: экстракция 4 промптов × 515 картинок на 2.2B в fp32 — порядка
15–30 минут на этой карте. Если сильно дольше — проверь, что реально используется GPU
(`nvidia-smi` в соседнем терминале).

## Шаг 3 — F4: другие семейства VLM (главная стадия, ~1–2 дня)

**Внимание: это не запуск одной командой.** Наш код умеет находить блоки внутри
SmolVLM (архитектура Idefics3): он ищет `model.vision_model`, `model.connector`,
`model.text_model`. У Qwen2-VL и LLaVA раскладка другая, поэтому `locate_stack` их не
найдёт и честно упадёт с понятной ошибкой — так задумано, чтобы не анализировать молча
половину стека.

Порядок такой:

**3.1 — снять раскладку модулей.** Для каждой новой модели выполни и пришли мне вывод:

```bash
uv run python -c "
import torch
from transformers import AutoModelForImageTextToText
m = AutoModelForImageTextToText.from_pretrained('Qwen/Qwen2-VL-2B-Instruct', dtype=torch.float32)
for n, c in m.named_children(): print(n, type(c).__name__)
print('---')
inner = getattr(m, 'model', m)
for n, c in inner.named_children(): print(' ', n, type(c).__name__)
print('--- ModuleLists ---')
for n, c in m.named_modules():
    if isinstance(c, torch.nn.ModuleList) and len(c) > 1: print(' ', n, len(c))
"
```

**3.2 — я пишу адаптеры** под каждую архитектуру и тесты к ним.

**3.3 — обязательная проверка перед прогоном.** У каждого нового семейства надо
побитово убедиться, что представления **действительно различаются** между условиями
задачи. Если визуальные токены окажутся до текста, эффект задачи невозможен архитектурно,
и мы получим ложный ноль. Это уже случалось на SmolVLM — проверка встроена в
`vlm_smoke_test.py`.

**3.4 — прогон и сводная фигура препринта:** наклоны `early`/`lateral` по слоям LLM,
все семейства и масштабы, точки = испытуемые.

**Вердикт стадии:** держится ли 0/8 по `early` вне SmolVLM. Это и отделяет
«наблюдение на одной линейке» от «эффекта».

## Если что-то идёт не так

| Симптом | Причина и что делать |
|---|---|
| `check_env` пишет `cpu` | не тот билд torch, переустанови с `--index-url .../cu124` |
| CUDA out of memory на 2.2B | что-то ещё занимает VRAM; закрой браузер/игры, проверь `nvidia-smi` |
| Очень медленно, GPU простаивает | модель осталась на CPU: в `configs/vlm.yaml` должно быть `device: cuda` |
| `locate_stack` падает на новой модели | так и задумано, см. шаг 3.1 — нужен адаптер |
| Кэш «уже посчитан», но картинок меньше | в кэше записано число картинок, несовпадение вызывает пересчёт; это нормально |

**Чего не делать:** не переходить на bf16 «чтобы влезло», не проверив шаг 1. И не менять
`prompt_position` — вопрос должен идти до картинки, иначе эффект задачи невозможен.

Коммиты засчитываются в contribution graph только если email автора привязан к аккаунту
GitHub. На новой машине git подставит что-то своё по умолчанию, поэтому задай явно:

```bash
git config user.name "Erdauit" && git config user.email "erdauttorehan@icloud.com"
```

Проверить, что коммит действительно привязался, можно так — если поле `author` не `null`,
значит GitHub сопоставил email с аккаунтом:

```bash
curl -s "https://api.github.com/repos/Erdauit/NSD-RSA/commits?per_page=1" | python3 -c "import json,sys; c=json.load(sys.stdin)[0]; print('привязан:', c['author']['login'] if c.get('author') else 'НЕТ')"
```
